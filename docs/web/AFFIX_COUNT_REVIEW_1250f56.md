## A1 / P2：抽中的条数被重复候选跳过逻辑削减

位置：`server/Nordicandia.Server/WebApi/LootTable.cs:135`。

循环执行 `affixCount` 次，但每次从完整候选池重新抽取；重复名称触发 `continue`，本轮仍占用一次循环。因此该数值实际控制的是尝试次数，而非最终词缀条数。当前候选池为 18 条。

独立探针固定槽位 12、品质 3、等级 10、普通类型，枚举种子 1–20000；使用生产代码相同的独立随机流，分别记录 `RollAffixCount` 返回值与 `CreateItem(...).Affixes.Count`：

| 条数 | 抽中次数 | 最终物品次数 |
|---|---:|---:|
| 0 | 12086 | 12086 |
| 1 | 2436 | 2562 |
| 2 | 2353 | 2424 |
| 3 | 1053 | 1207 |
| 4 | 1023 | 989 |
| 5 | 542 | 556 |
| 6 | 507 | 176 |

共 **1169/20000（5.845%）** 的最终条数低于抽样值。明确反例：种子 19 抽中 4 条，实际只有 3 条；种子 106 抽中 6 条，实际只有 5 条。

这不是权重采样本身错误，而是采样后的生成过程改变了条数分布。本次尚未独立证明原客户端遇到重复候选时如何处理，不能将任何补抽策略直接宣称为原版行为。

下一步应沿 `CreateItem/GenerateRandomAffix` 确认去重、重抽和容量处理。若抽样值代表目标数量，应在可用候选充足时补足，或使用符合原版约束的无放回选择；候选耗尽时明确退出规则。若原版也允许条数减少，应提供该分支证据，并将文档描述改为“目标条数权重已接入”。

## A2：独立随机流并未保持父提交的基础属性结果

位置：`server/Nordicandia.Server/WebApi/LootTable.cs:102`。

本次把父提交的 `LootTable` 复制到临时探针中，仅改类名以便与当前实现同时运行；依赖目录在此提交中没有变化。同一 `LootDrop` 和强制 Normal 类型下比较：

| 种子 | 物品定义（前后相同） | 物理最小伤害：父提交 → 当前 | 物理伤害增量：父提交 → 当前 |
|---|---:|---|---|
| 1 | 45 | 10.9779 → 10.9384 | 11.2417 → 11.4575 |
| 2 | 300 | 11.8083 → 13.8253 | 5.4087 → 5.9826 |
| 3 | 375 | 9.5335 → 9.6811 | 1.3082 → 1.8589 |

原因：旧版在基础属性抽样前，已用同一个 `rng` 消耗了若干次词缀随机数；新版改用 `affixRng` 后，主随机流停在更早的位置。

这不表示随机流隔离设计有问题，也不会自动修改已经保存的装备。它意味着跨版本相同种子的结果发生了一次变化。若无需兼容旧种子序列，明确记录生成算法版本和新基线即可；若必须兼容，应增加父版本对照测试，而不能只修改测试种子。
