# Nordicandia online-sync — status report (2026-09-27)

Consolidated status of the client-patch / server work that started with the v12
`.bss` crash and ended with working purchase sync for several features.

## TL;DR

* The long-standing "purchases don't reach the server" was **not** a server issue:
  the slot-expand stub's auth lookup used the wrong namespaces, so its
  `http_post()` returned before ever opening a socket.
* Several independent native-patch bugs have been fixed (ASLR resume, wrong hook
  addresses, wrong register passing, wrong operand order, wrong struct offsets).
* **Synced and server-persisted**: combat-pet unlock, skill-slot expansion,
  potion-slot expansion, combat-pet level/experience.
* **Still broken**: skill/potion slot counts still reset on relogin (client
  computes capacity locally); stash-page expansion; non-combat pet unlock;
  skill rank (unverified).

  (`patched_arm64/nordicandia.keystore`, pass `nordpass`, alias `nord`)

## 2. Root causes fixed

### 2.1 `.bss` out of the mapped RW segment (v12 crash)

The v12 slot-expand stub's writable state grew past the last RW `PT_LOAD`
`p_memsz` (ended at `0x5DE8800`), so the first store to `0x5DE9330` faulted
(`SIGSEGV SEGV_MAPERR`). Fixed by computing `STATE_END` from the linked stub
ELF's `.bss` (v13), and later by extending the segment to `0x5DEA000`.

### 2.2 Trampoline resume was not ASLR-safe

The first trampolines ended with `ldr x16, 0f; br x16; 0f: .quad RESUME`, where
`.quad` held the **link-time** VA. In a shared object that jumps to
`0x2E3DF44` instead of `base+0x2E3DF44` → `SEGV_ACCERR`. Fixed by using a
PC-relative `b <RESUME>` with the resume address supplied via `--defsym`
(same pattern the skill-rank stub already used).

### 2.3 Wrong registers passed to the C helpers

The helpers take `(type, cost)` / `(cost)`, but the trampolines called them with
the raw instance ABI (`x0=this, w1=type, w2=cost`), so the helpers read `this`
as the number and produced malformed JSON:

```
{"characterId":"…","expandType":,"opalCost":0}   -> 400
{"characterId":"…","opalCost":}                   -> 400
```

Fixed with `mov w0,w1; mov w1,w2` before the call.

### 2.4 Wrong auth namespaces → POST never sent

`refresh_auth()` looked up `find_class("Net","NetSession")` / `("Net","NetClient")`
and `SessionDto` in namespace `"Net"`. The real namespaces are
`Nordicandia.Client.Net`, `Client.Net`, `SharedNet.Dto`. So `find_class`
returned null, `g_ready` stayed 0, and `http_post()` returned before connecting.
Also the helpers read `g_guid` **before** `http_post()` ran `refresh_auth()`, so
even the first successful call sent an empty `characterId`.

### 2.5 Wrong hook addresses (`+0x4000` off)

Il2CppInspector-derived constants were consistently `+0x4000` off. Real addresses
(resolved live via the il2cpp API with Frida):

```
SkillGrid::ExpandSkillSlotOffline       0x252A3C8   (old 0x25263C8 = an epilogue)
InventoryGrid::ExpandPotionSlotOffline  0x250EA90   (old 0x250AA90 = other fn)
```

Skipped first instructions: `str x30,[sp,#-0x50]!` and `sub sp,sp,#0x90`.

### 2.6 Operand order in the "execute skipped instruction"

* combat pet: original is `stp x30,x25,[sp,#-0x40]!`; the stub wrote
  `stp x25,x30` → the epilogue loaded the return address from the wrong slot →
  `SEGV_ACCERR` "execute non-executable memory" when buying a pet.
* skill: skipped instruction was actually an epilogue `ldp x20,x19,[sp,#0x40]`.

### 2.7 Client enum vs server enum (skill slots)

Client `SkillSlotType` is 0-based; the server's `ExpandCharacterSkillSlotTypes`
reserves `0 = Unknown`. Send `skillSlotType + 1`.

### 2.8 Combat pet exp has no client→server path

The `CombatPet.set_Level/set_Experience` setters are **never** called on exp
gain. Traced path:

```
OfflineCombatPets.AddExperienceFromPotion
  -> CombatPetRules.AddExperience
     -> CombatPetMinion.SetPetParameters / RaiseLevelUp
```

Hook `CombatPetMinion::SetPetParameters` (`0x2A661D4`) and read the pet at
`[this+0x2B0]` (`DefinitionId@0x10`, `Level@0x18`, `Experience@0x20`).

## 3. Server endpoints added

New plain-HTTP (port 8081) JSON endpoints, all reusing the same `GameStore`
paths as the gRPC API:

| Endpoint | Request | GameStore call |
|---|---|---|
| `POST /api/character/expand-skill-slots` | `{characterId, expandType, opalCost}` | `ExpandSkillSlots` |
| `POST /api/character/expand-potion-slots` | `{characterId, opalCost}` | `ExpandInventoryRow(..., Potions, ...)` |
| `POST /api/character/combat-pet-exp` | `{characterId, combatPetDefinitionIntegerId, level, experience}` | `SaveCombatPetProgress` |

Already existing: `/api/character/skill-rank`, `/api/character/unlock-pet`,
`/api/character/unlock-combat-pet`, `/api/leaderboards`.

Client stubs POST raw HTTP/1.0 with `authorization: <NetSession.AuthToken>` and
a `characterId` from `NetClient.CurrentCharacterId`.

## 4. Remaining issues

### 4.1 Skill/potion slot counts reset on relogin (root cause found)

The server stores the correct `NumActiveSkillSlots` / `NumPotionSlots` and
returns them in `EnterGameWithCharacterResponse.GameModeAccountData`, but the
client ignores them:

* `SerializedPlayerGameModeAccountData` (wire type) **has** the slot fields;
* the runtime `PlayerGameModeAccount` (what the game holds) has **none of them**
  (`Logger,_StashContainer,_ArchivedStashContainer,NumStashPages,…`), so
  `PlayerGameModeAccount.Deserialize` drops them;
* the grid's capacity is computed locally. Disassembly of
  `ExpandSkillSlotOffline`:

  ```
  0x252A5E8  bl 0x2A86F50            ; -> current count (w24)
  0x252A5FC  bl SkillSlotRules::CanExpand(slotType, w24)
  ```

  Traced `CanExpand(slotType=0, cur=4)` during a session — the count comes from
  the local helper at `lib+0x2A86F50`, not from the server.

**Fix direction:** patch the client's capacity path (`0x2A86F50` / the
`SkillGrid` build) to add the server's purchased count, or have the server
persist the purchased capacity in the representation the grid rebuilds from.

### 4.2 Stash-page expansion

The four `WindowStash/WindowArchivedStash::Expand*StashPageOffline` methods never
fired when a page was expanded, so the UI uses a different path. Candidates:
`Game.Inventory::ExpandStashPage` (`0x2B8AA2C`),
`Game.StashContainer::ExpandStashPages` (`0x2BF7D90`),
`PlayerGameModeAccount::ExpandStashPage` (`0x2C173C4`). No server endpoint yet
(add one mapping to `GameStore.ExpandStashPage`).

### 4.3 Non-combat pet unlock

Server endpoint `/api/character/unlock-pet` already exists. The offline client
method has not been located yet (the `Offline*Pet*` classes found only contain
`OfflineCombatPets`; enumerate `OfflinePets`/pet-collection classes further).

### 4.4 Skill rank

`Game.LivingPowers::RankUp` (`0x2C6C63C`) is hooked and the endpoint
`/api/character/skill-rank` exists, but no POST has been observed — the UI may
use a different rank-up path.

## 5. Build / deploy tooling

* Full-chain build: `server/build_combined.py` (online → leaderboard → realtime →
  skill_rank → slot_expand → xp_drop). **Note:** local Homebrew/Apple clang makes
  the skill-rank stub exceed its `0x1000` cave (`check_cave_fit` aborts); the
  release builds bypass this because of a different toolchain. For the recent
  test builds the slot-expand stub was re-applied on top of the v14 release lib:
  `/tmp/nord_v15/mk_vNN.py`.
* XAPK packaging: `server/build_xapk_release.py <libil2cpp.so>` → signed XAPK in
  `dist/android-arm64-release/` (same keystore → in-place `adb install-multiple -r`).
* Server image: GitHub Actions `Build Lightsail image`
  (`gh workflow run "Build Lightsail image" --ref main`), then download the
  artifact, `docker load`, update `NORD_IMAGE` in `/opt/nordicandia/.env`,
  `docker compose up -d`.
* Device: Samsung `SM-S931U1` (`RFCY416VMHF`), frida-server 17.18.0.
  Device tooling: `adb`, `apksigner`, `zipalign`; runtime IL2CPP enumeration via
  the exported `il2cpp_*` API.
