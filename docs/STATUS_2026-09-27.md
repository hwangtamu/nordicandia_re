# Nordicandia online-sync — status report (2026-09-27, updated)

Consolidated status of the client-patch / server work that started with the v12
`.bss` crash and now covers slot, combat-pet, and passive-skill persistence.

## 1. Root causes fixed

### 1.1 `.bss` out of the mapped RW segment (v12 crash)
The slot-expand stub's writable state grew past the last RW `PT_LOAD` `p_memsz`.
Fixed by aligning `STATE_END` from the linked stub ELF and growing the segment.

### 1.2 Trampoline resume was not ASLR-safe
`ldr x16, .quad RESUME` held the link-time VA. Replaced with a PC-relative
`b RESUME` supplied via `--defsym`.

### 1.3 Wrong registers passed to the C helpers
The helpers take `(type, cost)`, but the trampolines passed the raw instance ABI,
producing malformed JSON. Fixed with `mov w0,w1; mov w1,w2`.

### 1.4 Wrong auth namespaces → POST never sent
`find_class("Net","NetSession")` was wrong; the real namespaces are
`Nordicandia.Client.Net`, `Client.Net`, `SharedNet.Dto`. Also `g_guid` was read
before `refresh_auth()` resolved the character id.

### 1.5 Wrong hook addresses (`+0x4000` off)
Il2CppInspector constants were `+0x4000` off. Real addresses were resolved live
via the il2cpp API.

### 1.6 Skipped-instruction/operand mistakes
`stp x30,x25` vs `stp x25,x30`, wrong epilogue operand, etc.

### 1.7 Client enum vs server enum
Client `SkillSlotType` is 0-based; the server reserves `0 = Unknown`. Send `+1`.

### 1.8 Combat-pet exp has no setter path
`CombatPet.set_Level/set_Experience` are never called on exp gain; the real path
is `CombatPetMinion.SetPetParameters` (`[this+0x2B0]` → `DefinitionId@0x10`,
`Level@0x18`, `Experience@0x20`).

### 1.9 Skill/potion slots were stored in the wrong representation
The client consumes slot capacity from **character attributes** (verified on
device: active 45, passive 56, training 49, potion 44), not from
`PlayerGameModeAccount` (the runtime type has no such fields). `SyncSlotCapacities`
writes the attributes and mirrors the account counters, with a one-time
`SlotCapacitiesMigrated` migration that reconstructs purchases from the old,
inaccurate initial values (caps 6/3/3/3).

### 1.10 Passive training never granted a level
Passive skills level through the time-based training system
(`LivingPowers.StartTraining` → `HasFinishedTraining`). The only caller of
`LivingPowers.RankUp` is `DuloGames.UI.UISlotBase.Unassign`, a UI coroutine that
started but **never reached** `ResetTraining`/`RankUp` on this build (it stalls
on its awaited UI tasks). Fix: hook `LivingPowers.StartTraining`, run its body,
then call the (patched) `LivingPowers.RankUp` so confirming a training grants the
level immediately. `RankUp` reports to `/api/character/skill-rank`, and
`LivingPowers.Serialize` uploads the full snapshot to `/api/character/powers`.

### 1.11 Exp gain was never applied (5M per-sync cap)
`RealtimeGateway.HandleMetadata` rejected any `BaseExperienceGained` over 5M as
"absurd". The xp10 build batches tens of millions between syncs (8.9M → 32.9M →
40.1M observed, all zeroed), so exp never applied. The client's unsynced total
then kept growing and the server's level stayed stale — which is also what made
attribute allocation overflow the (too-small) pool and error. Fix: add the gain
to the **persisted** experience (not the possibly-stale session cache) and raise
the sanity ceiling to 1e12.

### 1.12 Aesir offering used the offline path; blessing duration wrong attribute
The client applies Aesir offerings through
`WindowAesirOffering.MakeOfferingOffline` and **never calls the `MakeOffering`
gRPC**, so the blessing was local-only. Fix: capture the size from
`PromptOfferingPurchase`, POST it from `MakeOfferingOffline` to
`/api/character/make-offering` → `GameStore.MakeOffering` (durations
10m/30m/1h/4h for Small/Medium/Large/ExtraLarge).

On login, `DeserializeBlessing` rebuilds the buff and computes
`expiry = now + buff[Buff_Duration]`. **465 is the computed
`Buff_Duration_Total` = `(Buff_Duration + Bonus) × (1 + BonusPercent)`**, so
assigning it does nothing; the client recalculates from the base
`Buff_Duration`, which is **166**. Sending 465 left it `now + 0` → every blessing
treated as expired (UI and effect lost). Fix: send the base attribute 166 plus
the two context fields (`Buff_Context_Hash` 279 = 1, `Buff_Context_Type` 289 = 6)
with `IsCharacterContext = false`, matching the client's own
`FinalizeAesirBuffOffline`/`Serialize` output (verified on-device: 0 s with 465,
105.87 s with 166).

## 2. Server endpoints (plain HTTP/1.0 JSON on :8081)

| Endpoint | Request | GameStore call |
|---|---|---|
| `POST /api/character/expand-skill-slots` | `{characterId, expandType, opalCost}` | `ExpandSkillSlots` |
| `POST /api/character/expand-potion-slots` | `{characterId, opalCost}` | `ExpandInventoryRow(..., Potions, ...)` |
| `POST /api/character/combat-pet-exp` | `{characterId, combatPetDefinitionIntegerId, level, experience}` | `SaveCombatPetProgress` |
| `POST /api/character/skill-rank` | `{characterId, powerHashSafe, newRank}` | `UpgradeSkillRank` |
| `POST /api/character/powers` | `{characterId, powers:[{powerHashSafe,rank,trainingStart,trainingEnd}]}` | `SavePowers` |
| `POST /api/character/make-offering` | `{characterId, offeringType, offeringSize, offeredOpals}` | `MakeOffering` |

Already existing: `/api/character/unlock-pet`, `/api/character/unlock-combat-pet`,
`/api/leaderboards`.

`CharacterPowerServiceApiImpl.AssignPassiveSkillTraining` also persists the
training window (`Power_Training_Start/End`) and returns
`TrainingToLevel = currentRank + 1`.

## 3. Build / deploy tooling

* Full-chain build: `server/build_combined.py <orig.so> <out.so>` — applies
  online → leaderboard → realtime → skill_rank → slot_expand → xp_drop.
* XAPK packaging: `server/build_xapk_release.py <libil2cpp.so>` (same keystore →
  in-place `adb install-multiple -r`). Test devices: Samsung `SM-S931U1`
  (`RFCY416VMHF`), frida-server 17.18.0.
* Server image: GitHub Actions `Build Lightsail image` → download artifact,
  `docker load`, update `NORD_IMAGE`, `docker compose up -d`.
